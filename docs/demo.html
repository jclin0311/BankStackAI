1 · A bill payment, end to end

$45 electricity bill paid from a chequing account: synchronous accept with funds held, then an event-driven saga across four services and six Kafka topics, ending in a settled payment and a balanced ledger.

  1. 1

    Payment accepted, funds held

    client → payment-orchestrator :8086

    A bill payment is submitted with an Idempotency-Key. The orchestrator validates the biller against biller-service, places a hold on the debtor account via account-service (M2M OAuth2 client-credentials), persists the payment in FUNDS_HELD, and answers 202 with a status URL.

    HTTP POST /api/v1/payments/billpay — request
    {
  "debtorAccountId": "7e4c5d9a-d9ae-4d4f-b6e0-4c472d6f1519",
  "billerReferenceNumber": "HYDRO-001",
  "invoiceReference": "INV-2026-0815",
  "executionDate": "2026-08-15",
  "amount": {
    "currency": "CAD",
    "value": 45.0
  },
  "note": "August electricity bill"
}
    HTTP 202 Accepted — response
    {
  "paymentId": "0b8c5c51-0c7d-4bf3-b06d-2f7e7183bca0",
  "state": "FUNDS_HELD",
  "statusUrl": "/api/v1/payments/0b8c5c51-0c7d-4bf3-b06d-2f7e7183bca0"
}

2 · A natural-language request through the AI layer

One sentence travels multi-agent → Ollama → MCP server → account-service and back. The caller's JWT is relayed across every hop, so the AI layer never escalates privileges.

  1. 1

    Natural-language request

    client → multi-agent :8096

    One sentence in; the gateway authenticates the caller's Auth0 JWT and passes the message to the agent.

    HTTP POST /api/v1/agent/chat — request
    {
  "message": "Show me the recent transactions for account 7e4c5d9a-d9ae-4d4f-b6e0-4c472d6f1519"
}
  2. 2

    Intent routing and argument extraction

    multi-agent → Ollama (llama3.2, local)

    The LLM decides this is a tool call and extracts structured arguments — note the correct accountId pulled out of free text.

    LLM routing decision — from the actual response

  3. 3

    MCP tools/call with the caller's JWT relayed

    multi-agent → mcp-server :8095

    The agent invokes the tool over MCP (streamable HTTP). The user's bearer token rides the request, so the MCP server authenticates the original caller — zero trust preserved across the agent hop. The server writes a per-tool audit line.

The same chain, refusing correctly

Before the machine client was granted the admin tool role, the identical question produced this instead: the JWT authenticated fine, the tool executed — and refused, because a client-credentials token carries no customer_id claim, and customer-role tools will not return account data without knowing whose data it is. Denials are audited with the same fidelity as successes.
